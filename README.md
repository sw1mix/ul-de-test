# Коридор ставок и прогноз тарифа

Небольшой прототип аналитического слоя для платформы грузовых ставок: почистить сделки, собрать помесячную карточку маршрута и получить пакетный прогноз тарифа за рейс.

Стек простой намеренно: PostgreSQL 17 и Python. Без Airflow, Superset и ClickHouse — чтобы проверка закрывалась одним `docker-compose up`, без лишних движков.

## Картина целиком

Операционка лежит в `public` — схема и генератор из пакета задания (`sql/source`, 300 000 сделок, снимок на `2026-10-26`). Пайплайн её не трогает.

Дальше два своих слоя:

- `core` — сделки после DQ: цена в рублях без НДС, одна строка на пару «сделка × группа кузова». Города схлопнуты до одной записи на `gc_id` (берём минимальный `cities.id`).
- `mart` — витрина `mart.route_card` и прогнозы `mart.ml_price_predictions`.

Очистку и витрину крутит SQL в Postgres. Python только задаёт окно дат, гоняет загрузку и пишет журнал. Повтор того же окна не плодит дубли: сначала delete окна, потом insert, всё в одной транзакции. Витрина каждый раз собирается заново из `core`. Перед сдачей пайплайн прогоняет загрузку дважды и сверяет число строк и суммы — чтобы убедиться, что идемпотентность живая.

Модель — `CatBoostRegressor` (400 деревьев, глубина 6, seed 42). Рядом в лог пишется простой Ridge на тех же числовых признаках, без категорий — как sanity-check. В таблицу прогнозов уходит только CatBoost.

## Запуск

Нужен Docker.

```bash
docker-compose up --build --abort-on-container-exit --exit-code-from pipeline
```

`docker-compose up --build` делает то же самое, но терминал зависает на логе Postgres после расчёта. Первый старт долгий: база сама накатывает `sql/source/schema.sql` и `sql/source/synthetic.sql`. Пайплайн ждёт таблицу `public.source_ready` (её создаёт последний init-скрипт). Одного `pg_isready` мало — сервер уже принимает коннекты, пока генератор ещё пишет данные.

Повторный запуск с заполненным томом базу заново не генерирует. Чистый пересчёт:

```bash
docker-compose down -v
docker-compose up --build --abort-on-container-exit --exit-code-from pipeline
```

Postgres с хоста: `127.0.0.1:54329`, пользователь `deals`, база `deals_bigdata`. Пароль в `docker-compose.yml` / `.env.example` — локальный, для прототипа.

Пересчитать окно без пересборки образа:

```bash
docker-compose run --rm -e START_DATE=2026-10-01 -e END_DATE=2026-10-31 pipeline python -m etl
```

Это обновит `core` за октябрь и пересоберёт витрину по всему `core`. Модель отдельно: `python -m ml` или полный `python -m run`.

## Что отсекаем при очистке

Битая строка в `core` не попадает. Она уходит в `core.dq_quarantine_prices` с одним кодом — по первому сработавшему правилу:

| Код | Условие |
| :--- | :--- |
| `PRICE_NON_POSITIVE` | `price <= 0` |
| `RUB_PRICE_LE_1000` | рубли и `0 < price <= 1000` |
| `DISTANCE_NON_POSITIVE` | `distance <= 0` |
| `WEIGHT_NEGATIVE` | `total_weight < 0` |
| `VOLUME_NEGATIVE` | `total_volume < 0` |
| `CITY_NOT_IN_DIM` | города отправления или назначения нет в `cities` |
| `FX_RATE_MISSING` | валюта не рубль, точного курса на `nearest_rate_date` нет |

Одинаковый город погрузки и выгрузки не режем: в источнике такие пары есть, и это ок.

Рубли (`643`) берём как есть, курс 1. Доллар (`840`) и евро (`978`) множим на курс с `nearest_rate_date`. Эта дата в источнике завязана на `created_at`, не на дату погрузки. Курса нет — строка в карантин. Подстановки курса на `loading_date` нет.

Пустые `weight_category` / `volume_category` заполняем по весу (округление до 0,1 т) и по объёму. Уже заполненное не переписываем. Вес: `G20T` от 30 т, `FTL` 10–30, `10T` 5–10, `5T` 2,5–5, `L5T` 0,5–2,5, иначе `OTH`. Объём: `FTL` при `0 < V <= 120`, иначе `OTH`.

`outlier_mark` сами не пересчитываем. В витрину и в обучение строки с `outlier_mark = true` не берём. Сделки от 26 октября 2026 после ночного прогона разметки в генераторе остаются с `outlier_mark = false`, даже если цена странная — так устроен снимок, не баг фильтра.

## Витрина маршрута

Зерно `mart.route_card`: месяц × город отправления × город назначения × группа кузова × весовая категория. Месяц — из `price_dates.price_date`, поэтому длинная заявка может лечь в несколько месяцев. `volume_category` в зерно не входит.

Группа кузова одна на сделку и группу, даже если в `price_body_types` два дочерних кода одного стандарта:

- Тент — `56–61`, `std_id = 56`
- Рефрижератор — `4, 46, 47, 48`, `std_id = 4`
- Изотерм — `2`
- Борт — `1, 15`, `std_id = 15`
- Прочие — остальные коды
- Не указан — кузова нет ни в связи, ни в `prices.body_type`

В ячейку идут только факты (`is_fact`, типы `1, 2, 3, 4, 5, 9`), прямые рейсы (`complex = false`), с положительными ценой в рублях и дистанцией, без выброса. Месяц позже `2026-10-26` в историю не берём.

Метрики: P25 / P50 / P75 и среднее за рейс, те же перцентили за км (`price_rub / distance`), число сделок, число перевозчиков (`organization_id` при типе `3` или `9`), коэффициент вариации. `MoM` / `YoY` — сдвиг медианы к прошлому месяцу и к тому же месяцу год назад. Нет соседней ячейки или медиана нулевая — в поле `NULL`, чужой месяц не подставляем.

`reliability_level`:

- `HIGH` — ≥30 рейсов, ≥5 перевозчиков, и конец месяца не старше 30 дней от `2026-10-26` (октябрь — возраст 0, сентябрь ещё ок, август уже нет);
- `MEDIUM` — ≥10 рейсов;
- иначе `LOW_DATA`.

Примеры запросов — `sql/examples.sql`.

## Прогноз

Цель — `price_rub` за рейс без НДС. Учимся только на фактах, прямых рейсах, без выброса. Сплит по дате погрузки, `as_of = 2026-10-26`:

- train: с `2026-07-26` включительно до `2026-10-05` не включительно;
- test: `2026-10-05` … `2026-10-26` включительно;
- будущие заявки: `loading_date > 2026-10-26`.

Без случайного shuffle. Граница 5 октября только в test.

Признаки: дистанция, вес, объём, координаты и регион отправления/назначения (регион — кусок `full_name_local` после запятой), город, группа и тип кузова, весовая и объёмная категории, год и sin/cos месяца, дня недели и дня года. Месяц по модулю 12, чтобы декабрь стоял рядом с январём. День недели: понедельник = 0. Период дня года — 365,25.

В признаки не тащим цену, цену за км, `outlier_mark`, курс и агрегаты `price_group_stats`. Для модели группа кузова — из `prices.body_type`, а не размножение по всем группам связи (иначе одна цена уехала бы в обучение несколько раз). Кузов пустой — берём первую группу из связи.

На test в лог и в `artifacts/metrics.json` пишутся R², MAPE, RMSE, MAE. Прогнозы test и будущих заявок — в `mart.ml_price_predictions`. У будущих строк `actual_price_rub`, `abs_error_rub` и `ape_pct` пустые, даже если в источнике цена уже есть.

## Метрики на снимке

Считаются при `docker-compose up`, лежат в `artifacts/metrics.json`.

Прогон на 300 000 сделок, seed 42. Train 24 226, test 12 808, будущие 5 998.

| Модель | R² | MAPE | RMSE, руб. | MAE, руб. |
| :--- | ---: | ---: | ---: | ---: |
| CatBoost | 0,921 | 15,82% | 53 812 | 27 927 |
| Ridge, только числа | 0,801 | 42,27% | 85 406 | 52 906 |

В карантин ушло 203 строки: 164 с нулевой ценой и 39 в валюте без курса на `nearest_rate_date`. Правило «рубли ≤ 1000» на этом генераторе ни разу не сработало — в коде оно есть. Повторная загрузка того же окна не сдвинула число строк и сумму `price_rub`.

## Проверки

```bash
python3 -m pytest -q
```

Тесты без базы фиксируют пороги веса/объёма, порядок причин карантина, границу train/test, свежесть `HIGH`/`MEDIUM`/`LOW_DATA`, пустой MoM без соседа и запрет целевой цены в признаках. В контейнере пайплайн дополнительно сверяет те же пороги уже функциями Postgres, равенство `source = core + quarantine`, отсутствие будущих месяцев в карточке и пустой факт у будущих прогнозов.
